Procedure and trust policy

The work is organized as a pipeline in which drafting is cheap and trust comes only from the Lean kernel. Proof drafts are written by AI coding agents working in parallel. A supervising session verifies each result before it enters the repository.

The pipeline

  1. Fix the statement.The definitions of an odd perfect number and of the conjecture are written first and kept minimal, so that every later theorem can be read against them.
  2. Survey the literature and existing code.Papers and public repositories are screened, the relevant ones are read in full, and each gets a note: the method, the lemmas worth formalizing, and any step that does not hold up. See the survey.
  3. Assign one module per agent.Each agent receives a precise target statement, the proof standards, and pointers to the existing library. Agents write new proofs on top of the existing library, test claims numerically with exact arithmetic before formalizing them, and may only check their own file.
  4. Report deviations.An agent must say exactly what it proved, what it could not prove, and where it changed a statement. Statements found to be false are corrected and the counterexample is recorded.
  5. Verify independently.For every returned module the supervising session scans for forbidden constructs, runs a full build of the whole library, parses every axiom report printed by the build, and reads the headline statements against their intended meaning. The verification steps are listed below.
  6. Commit only verified work.A module is committed and pushed only after the full build succeeds and every axiom report is clean.
  7. Test ideas against countermodels.Objects that satisfy most of the constraints without being odd perfect numbers, such as spoof factorizations, are kept as formal test cases. A proposed global argument that these objects also satisfy cannot be a proof. See Why it is hard.
  8. Steer the next wave.A review of the library, the notes, and the countermodels produces a ranked list of next targets, and the cycle repeats. See the roadmap.

Trust policy

A reader should need to trust only the Lean kernel, mathlib, and the statements themselves.

No escape hatches

The library contains no sorry, no admit, no added axiom, no native_decide, and no unsafe or implemented_by declarations. The site generator counts these tokens outside comments in every file of the main branch; the count for commit e489fe6 is 0.

Three axioms only

The modules end with #print axioms lines for their theorems, and every report must list at most propext, Classical.choice and Quot.sound. The exceptions are listed under axiom report coverage below.

Computation inside the kernel

Finite case analyses are run by verified checkers and evaluated with kernel reduction (decide +kernel). Primality of large numbers uses Pratt certificates checked the same way, or primality witnesses checked through mathlib's lucas_primality.

Pinned environment

leanprover/lean4:v4.33.1 with mathlib pinned to a fixed commit. The whole library is rebuilt before every commit.

Untrusted inputs

Papers and third party code are read as data only. Nothing from them is executed or copied into the library, and every borrowed statement is proved again in Lean.

Untrusted search

Certificates, proof trees and tables are found by programs outside Lean, published under scripts/ in the repository. They are not trusted: each certificate is a literal in a Lean file and the kernel checks it again, so an error in a search program can make a search fail but cannot make a false theorem pass.

Honest naming

Partial results carry their exact hypotheses in the statement. A theorem is never weakened silently to make a proof go through.

Provenance of the seed

The eight modules under OddPerfect/Seed/ are the project's own earlier starter code, imported at the start of the repository. Everything else in the library was written on top of them.

Continuous integration

The main branch contains a continuous integration workflow (.github/workflows/axiom-gate.yml). It restores the compiled library of the most recent passing run on the main branch and rebuilds only the modules whose sources or imports changed; a weekly run and a manual run rebuild everything from an empty build folder. The three standard axioms

Lean's kernel checks proofs in a small type theory. A handful of axioms are added by the core library, and mathlib uses three of them throughout. A theorem that depends only on these is proved in ordinary classical mathematics.

propext
Propositional extensionality: two propositions that imply each other are equal. It lets a proof rewrite a statement by an equivalent one.
Classical.choice
The axiom of choice in type form: from a proof that a type is nonempty it produces an element of it. Together with the other two it implies the law of excluded middle, so proofs by contradiction and case splits on any proposition are allowed.
Quot.sound
Soundness of quotients: elements related by a relation become equal in the quotient type. Function extensionality (functions that agree everywhere are equal) is derived from it.

Forbidden constructs

sorry and admit
Placeholders that close any goal without a proof. They elaborate to the axiom sorryAx, which would appear in every axiom report downstream.
axiom
A declaration that asserts a statement without proof. Any added axiom could be false, and then everything would follow from it.
native_decide
Decides a computable proposition by compiling the decision procedure to native code and running it. The kernel then trusts the compiler and the runtime instead of checking the computation itself; the proof depends on extra axioms such as Lean.ofReduceBool.
unsafe, implemented_by, @[extern]
Ways to give a definition code that the kernel does not check, or to replace its compiled behavior with other code. They are excluded so that what is evaluated is exactly what is proved about.

What decide +kernel does

For a proposition with a Decidable instance, decide proves it by evaluating the instance to true. With the +kernel option the evaluation is done by the kernel's own definitional reduction rather than by the elaborator, and the resulting proof term is checked by the kernel like any other. No axiom is added and no compiled code is trusted. The price is speed, which is why the checkers in the library (Cert.check, Pratt.check, checkSupport) are written with structural recursion and simple arithmetic, so that the kernel can reduce them.

How #print axioms works

The command #print axioms T walks through every declaration that the proof of T uses, transitively, and lists the axioms it reaches. During a build each such line prints a message of the form 'OddPerfect.steuerwald' depends on axioms: [propext, Classical.choice, Quot.sound]. A theorem that used sorry would list sorryAx, and one that used native_decide would list an extra axiom such as Lean.ofReduceBool.

Verification steps for each module

  1. Scan.The new file is scanned for sorry, admit, axiom, native_decide, unsafe, implemented_by and extern.
  2. Full build.lake build of the whole library, not only the new file, so that every import and every downstream module is checked together.
  3. Axiom reports.Every "depends on axioms" line in the build output is parsed, and the module is rejected if any line lists an axiom outside propext, Classical.choice and Quot.sound.
  4. Read the statements.The headline theorems are read against their intended meaning: the hypotheses, the conclusion, and whether a statement was weakened.
  5. Commit and push.Only then is the module committed and pushed to the main branch.

Reproduce the build

Install elan, the Lean version manager, then:

git clone https://github.com/adamrsophie/OddPerfectNumber.git
cd OddPerfectNumber
lake exe cache get
lake build
python3 scripts/Controls/source_scan.py
lake env lean AxiomGate.lean
lake env lean StatementGate.lean
sh GateControls/run.sh AxiomGate.lean StatementGate.lean

lake exe cache get downloads the prebuilt mathlib files for the pinned commit, so that only this library is compiled. The build prints the axiom report of every theorem listed in a #print axioms line. The command lake env lean AxiomGate.lean runs the whole library axiom check: it inspects every constant defined in the library, private ones included, and fails if any depends on an axiom outside the three standard ones. scripts/Controls/source_scan.py scans the sources for constructs that check cannot see after the build and verifies that the root file imports every module. StatementGate.lean restates the headline theorems with the definitions of mathlib and the predicate OddPerfect only, and checks the restatements against a fixed list, so none can be dropped or added without notice. The last command runs the checks on their control files: files that must be accepted and files that must be rejected, each for a stated reason.
