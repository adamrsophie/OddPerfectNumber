# Search and generator scripts

These are programs that found certificates, proof trees, tables and primality witnesses used in the Lean library `OddPerfect`. The folder is not complete; see the last section. Nothing in this folder is trusted: every certificate these scripts produce is checked again by the Lean kernel inside the library, so a bug here can make a search fail but cannot make a false theorem pass. The scripts exist so that the searches can be repeated and extended.

## Requirements

* Python 3 (version 3.12.14 was used). Most scripts need only the standard library.
* sympy (version 1.14.0 was used) for `ExponentTenTwelve/gen.py`, `ExponentTenTwelve/explore.py`, `CommonPrimeChain/gen.py`, the three scripts in `CommonFamily/`, `CommonFamilies/search.py`, `verify.py` and `gen2.py`, `KanoldFive/check.py`, `EqualExponentChainMore/gen2.py` and `nt.py`, and `Restrained/gen13.py`.
* `LowerBound/gen.py` and `LowerBound/emit.py` use cypari2 (version 2.2.4 was used) for factoring; without it they fall back to Pollard rho and ECM and may produce a different tree.
* numpy for `ForcingClosedBound/check.py`.
* `ThreeFreeThree/` reads its compressed certificate with the standard module `lzma`, present in most Python builds.
* A C compiler for `EqualExponentChain/osearch.c`: `cc -O2 -o osearch osearch.c`. `EqualExponentChainMore/gen2.py` uses the same program, looked up in the folder `EqualExponentChain`.

Each script starts with a header that says what it computes, which Lean declaration uses the result, how to run it and roughly how long it takes. Scripts read and write their data files in the current folder and find their helper files next to themselves, so they can be run from any folder.

## Validator controls

`Controls/validator_controls.py` checks that four validators fail closed, for people and automation that read only the exit status: `EqualExponentChain/checker.py`, `LowerBound/check.py`, `CommonFamilies/verify.py` and `CommonFamilies/est.py`. The first three use the same exit status convention: 0 when everything given passes, 1 when a well formed input fails a check (a rejected certificate, table or tree, a deficient case, a missing or extra case, a claim that differs from `--expect`), 2 for malformed input or a usage error (unreadable JSON, duplicate keys, an unknown node tag or a wrong number of fields, duplicate rows or cases, a residue outside `0 ≤ r < m`, no certificate or tree given, a requested tree absent from the file). `est.py` stops with status 1, before it writes anything, when a target cannot be reached (a whole pass adds no node), where it used to loop forever. None of the four relies on `assert`, so `python3 -O` gives the same verdicts.

Without `--expect`, OK from `verify.py` means only that the certificate proves the statement it declares itself. To check a certificate against the claim of a named theorem, state that claim; for the certificates in `certs/`:

    python3 -I verify.py --expect '{"d": 5, "seeds": [5, 7], "special_test": [12, 1], "excluded_primes": [], "exponents": {}}' certs/cert_d5_7.json
    python3 -I verify.py --expect '{"d": 65, "seeds": [5, 13], "special_test": [12, 1], "excluded_primes": [], "exponents": {}}' certs/cert_d65.json

The control script runs each validator as a subprocess, in normal and in optimized mode, on every archived valid input (status 0 expected) and on mutated copies built in a temporary folder (unknown node tag, extra field on the node `mod4`, a well formed certificate that fails, truncated JSON, a changed split instruction and a wrong table witness in a copy of `OddPerfect/LowerBound.lean`, a deficient singleton certificate, a conflicting duplicate case, a missing case, an extra case, the empty residue profile `(1, 1)`, the excluded prime `1`, a duplicate row, a claim that differs from `--expect`, and an `est.py` table whose target cannot be reached, run with a 20 second limit). Each mutation must give its exact expected status and no Python traceback. It also checks that none of the four validators contains an `assert`. It writes nothing inside the repository, prints one line per control and a final count, and exits 0 only if every control behaves as expected. Run it from any folder (about half a minute):

    python3 -I scripts/Controls/validator_controls.py
    python3 -I scripts/Controls/validator_controls.py --stdlib-only

The same script holds the controls of the helpers under `ThreeFreeThree/` (standard library only, so they run in both forms). `check3.py` used to accept three malformed leaves: a fifth weight (the four slot loop ignored it, the tail sum did not), a negative square witness `s` (the test `d = (2 s + 1)^2` cannot tell `s` from `-(s + 1)`), and a leaf with three slots. It now requires exactly four slots and four weights and natural number witnesses; each of the three forged certificates was accepted before the change and is rejected now with status 1. `verify3.py` rejected all three before and after. Three runs that printed their failures now also end with status 1: `gen_lean.py <certificate> mirror` on a disagreement, `route3.py` on a routing failure, and `verify3.py --tamper` when a tamper is not rejected (controlled with a copy of `verify3.py` whose tamper loop skips the verifier). The controls also run both checkers, the tamper list, the mirror and the deterministic part of `route3.py` (`<certificate> 0 1`) on the published certificate, and regenerate the twelve modules with `gen_lean.py <certificate> data` into the temporary folder and compare them byte for byte with the files in `OddPerfect/`. None of this changes a Lean file or the certificate.

The controls of `verify.py` need sympy; without it the first form fails, and the second skips them and lists each as SKIP. The validators run as subprocesses of the interpreter that runs the control script, so a virtual environment interpreter gives them its own packages, also in isolated mode (`-I` drops `PYTHONPATH` and the user site folder, not the site folder of the environment).

The continuous integration workflow runs the first form, all controls, before the build. The system Python of the runner has no sympy and is externally managed, so the workflow creates a virtual environment outside the checkout and installs into it exactly the pinned wheels of `Controls/requirements-sympy.txt` (sympy 1.14.0 and mpmath 1.3.0, both pure Python `py3-none-any` wheels, so the hashes hold on every platform) with `pip install --require-hashes`; pip refuses a file with any other hash. The requirements file says how to regenerate its hashes. The next step runs `CommonFamilies/rebuild95.sh` with the same interpreter, which the script takes from the environment variable `PYTHON` (default `python3`):

    python3 -m venv /tmp/venv
    /tmp/venv/bin/python -m pip install --require-hashes -r scripts/Controls/requirements-sympy.txt
    /tmp/venv/bin/python -I scripts/Controls/validator_controls.py
    PYTHON=/tmp/venv/bin/python bash scripts/CommonFamilies/rebuild95.sh . /tmp/rebuild95

Local run of these four steps (2026-11-22, Python 3.12.2 of python.org, a copy of `scripts/` and `OddPerfect/` in a scratch folder, a `PATH` whose `python3` has no sympy): pip installed `mpmath-1.3.0 sympy-1.14.0`; the controls printed `validator controls: 56 passed, 0 failed, 0 skipped`, exit 0 (73 with the controls of `ThreeFreeThree/` added later: 49 passed and 24 skipped with `--stdlib-only` on a machine without sympy); the rebuild printed `byte equal: 19 of 19 modules`, exit 0 (5.6 s wall). With one hash digit changed pip stopped with a hash mismatch. Without `PYTHON` the rebuild ran the `python3` of that `PATH` (`/usr/bin/python3`, which has no sympy) and stopped with exit 1 at its first step that needs a newer Python, so the variable is what selects the interpreter.
